# Page overview

Document pages have personal **Overview / Document** view selection. The document editor stays mounted while hidden, so switching preserves editing state and cloud updates. Database views and the guided first-start page keep their existing presentation.

An editor explicitly generates a structured overview using the existing `page.overview` AI purpose, provider routing, data rules and budget accounting. It reads the current page's full text snapshot, including textual table/code content, but does not fetch linked pages, Atlas evidence or attachments. Every card must contain an exact quote and a valid source-block reference. This validates the link to the page; it does not independently validate the page's claims. Inputs over 120,000 serialized characters stop before inference instead of being silently truncated.

The cached overview is bound to a SHA-256 signature of the title and document. Opening it makes no model request. A source change marks it outdated and disables adopting decisions/actions until it is regenerated. Concurrent source/overview changes during generation reject the result. Cancellation, workspace changes and permissions are checked before saving. An outdated source jump refuses to land on a different passage.

Human reviews are separate from generated cards. Each retains its item snapshot, signature, timestamp, author, response, optional responsible person and adopted task reference. Regeneration keeps reviews, flags changed foundations and shows unmatched reviews in an earlier-items section. Confirming a decision requires an explicit note. Adopting a step creates a child document containing an ordinary indexed One task and source link; repeat adoption on the same client reuses that task. New child pages inherit cloud privacy through the existing binding. No external tickets or notifications are sent.

Cloud metadata stores the overview as one scalar and reviews as individual `overviewReview:<item-id>` keys on the existing page Y.Map. This avoids a first-write race from creating competing nested maps. Distinct concurrent reviews merge; the same entry follows Yjs conflict resolution. Editing UI detects a remotely changed review and preserves the unsaved input for comparison. The existing client/server authorization boundary applies. A page accepts at most 200 review entries; reaching that bound is reported without discarding earlier entries.

Verification: `tests/unit/page-overview.test.ts` covers citation validation, limits, sanitization and concurrent Yjs review merge. `tests/e2e/page-overview.spec.ts` covers generation, persistence, stale sources, review/task adoption, cancellation, permissions, races and responsive themes. Provider responses are mocked; tests do not incur model usage.
