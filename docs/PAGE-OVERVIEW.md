# Page overview

Document pages have personal **Overview / Document** view selection. The document editor stays mounted while hidden, so switching preserves editing state and cloud updates. Database views and the guided first-start page keep their existing presentation.

An editor explicitly generates a structured overview using the existing `page.overview` AI purpose, provider routing, data rules and budget accounting. It reads the current page's full text snapshot, including textual table/code content. An explicit source picker can add up to 30 ordinary descendant pages (including deeper descendants) in the same visibility scope. Databases, their rows, hidden/trash branches and follow-up records are excluded. Other links, Atlas evidence and attachments are not fetched. Every card must contain an exact quote and a valid source-block reference. This validates the link to the page; it does not independently validate the page's claims. Inputs over 120,000 serialized characters stop before inference instead of being silently truncated.

The cached overview is bound to a SHA-256 signature of the title and document, plus each explicitly selected descendant's title and document. Newly created descendants are not silently added to a saved selection. Selected descendants stay subscribed while the overview is mounted; generation loads up to four at a time and retains subscriptions through final validation. A missing, moved, hidden or differently scoped descendant invalidates the result. Each generated citation carries host-assigned page/block provenance; the model cannot forge it. Opening it makes no model request. A source change marks it outdated and disables adopting decisions/actions until it is regenerated. Concurrent source/overview changes during generation reject the result. Cancellation, workspace changes and permissions are checked before saving. An outdated source jump refuses to land on a different passage.

Human reviews are separate from generated cards. Each retains its item snapshot, signature, timestamp, author, response, optional responsible person and adopted task reference. Regeneration keeps reviews, flags changed foundations and shows unmatched reviews in an earlier-items section. Confirming a decision requires an explicit note. Adopting a step creates a child document containing an ordinary indexed One task and source link; repeat adoption on the same client reuses that task. New child pages inherit cloud privacy through the existing binding. No external tickets or notifications are sent.

Cloud metadata stores the overview as one scalar and reviews as individual `overviewReview:<item-id>` keys on the existing page Y.Map. This avoids a first-write race from creating competing nested maps. Distinct concurrent reviews merge; the same entry follows Yjs conflict resolution. Editing UI detects a remotely changed review and preserves the unsaved input for comparison. The existing client/server authorization boundary applies. A page accepts at most 200 review entries; reaching that bound is reported without discarding earlier entries.

Verification: `tests/unit/page-overview.test.ts` covers citation validation, limits, sanitization and concurrent Yjs review merge. `tests/e2e/page-overview.spec.ts` covers generation, persistence, stale sources, review/task adoption, cancellation, permissions, races and responsive themes. Provider responses are mocked; tests do not incur model usage.

Generation shows real phases (snapshot preparation, waiting for model text, receiving cards, final checks/save) and elapsed time, with no invented percentage or ETA. Direct Claude structured requests stream JSON in the same single metered request; existing neutral/worker routes may buffer until their contract and policy checks finish. The summary is requested first. An incremental scanner publishes only complete, bounded, source-quoted cards, handling string escapes across chunks. These cards are explicitly provisional and cannot be adopted or reviewed. The final response still passes the task contract, full JSON/source validation and concurrency checks before replacing the saved overview. Cancelling or failing removes previews and retains saved content. No retry starts after streamed text has been emitted. Reading the document during generation preserves the chosen view at completion.

The progress tests hold a real browser response stream open, assert an early card before completion/persistence, then finish, interrupt or cancel it. They also verify document navigation, mobile layout and preservation of the previous saved overview. These are mocked provider streams, not a benchmark of provider response latency.


## Page-specific follow-up

An editor may select any saved, current overview cards and explicitly transfer the selection into an ordinary child database named Follow-up / Nachverfolgung. The database contains status, type, owner, due date, source page and suggested responsibility area. Each row retains the proposal text, options, done-when condition and original source link/quotation. Selection is not a confirmed decision or an assignment; owner and due date start empty.

The database and rows have deterministic identities derived from the originating page and card, plus sanitized `overviewFollowUp` provenance in page metadata. Repeating a selection reuses an existing entry without overwriting its status or edited content, even when the original overview is regenerated. Existing trashed entries are not silently recreated. The database inherits the parent's cloud privacy scope; a locked, trashed or differently scoped destination is rejected. Ordinary database editing and cloud synchronization apply. Distinct root pages always have distinct follow-up databases. The follow-up database is excluded from overview source selection.
